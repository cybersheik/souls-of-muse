# 0002. Lesson slots never expire by time

- **Status:** Accepted
- **Date:** 2026-10-27
- **Workstream:** 01 Service and lesson
- **Decided by:** project owner
- **Prepared with:** generated by Muse Wonder, independently reviewed by Muse Spark; integration and tests by the integrator agent

## Context
The first release must run at most five simultaneous live lessons on one machine. Each lesson starts an external media room. If the system loses track of a room (crash, timeout, uncertain provider response), it can believe a slot is free while a real room is still running and costing money.

## Options considered
1. **In-memory counter.** Lost on restart, wrong across processes.
2. **Time-to-live slots.** Self-healing, but a slot can be freed while the real room is still alive.
3. **Durable state machine with explicit terminal transitions.** Slots are freed only by confirmed events.

## Decision
Option 3 on SQLite (`BEGIN IMMEDIATE`, shared database file on one persistent VM):
- `STARTING`, `ACTIVE` and `CLOSING` all hold a slot until an explicit terminal transition.
- A durable "provisioning started" flag is committed **before** the external room is created.
- An uncertain outcome leaves the slot occupied for operator reconciliation.
- Stored capacity (at most 5) is the single authority. A mismatch fails closed.

## Consequences
- The system can under-admit after a failure, but never over-admit.
- Horizontal scaling needs an atomic shared database passing the same conformance tests. That boundary is documented, not implemented.
- These tests prove **admission concurrency only**. No media capacity or five-room voice benchmark is claimed.

## Verification
`tests/test_lesson_admission.py` covers:
- multi-process admission races;
- restart behaviour;
- uncertain external provisioning;
- schema validation;
- identifier regressions.
